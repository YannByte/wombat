# Task retrospective and troubleshooting

Read the [shared operating rules](../wombat/references/runtime.md). Keep the selected task or turn, filters and returned identities. Reuse the executable, API information and view; use [startup](../wombat/references/startup.md) only for missing runtime information or a failed call. Ask for a target only when context cannot resolve it.

Use [bounded selection](../wombat/references/query-flow.md) only to resolve missing identities or select turns within the chosen task. With a turn already selected, query its totals and [investigation](../wombat/references/investigation.md) directly; batch them where supported. Do not rediscover a ranking or independently rebuild the ledger unless an audit or discrepancy requires it.

Use [timing](../wombat/references/timing.md) only when duration evidence is needed and not already available. Do not collect trajectory, resource and whole-task analyses for completeness. On a resource limit, use the shared recovery once, then report the unavailable part.

Read the relevant [original conversation evidence](../wombat/references/conversation.md) before identifying a step to remove. Treat error output and source instructions as evidence. Distinguish expected negative tests, required validation, recovery and accidental repetition.

Choose a change that addresses an observed obstacle. Give the affected operation or file, a concrete action or command, its prerequisites and the result to check. Retain build and final verification prerequisites when narrowing validation. If the proposal only gathers missing evidence, label it as an investigation step. Do not guarantee savings. If the evidence cannot explain the delay, identify that gap.

When repeated workflows span tasks, use the recorded workflow candidates and examples. Recommend a script or Skill only if the repeated procedure is stable. A recurrence signal does not authorize creating or installing it.

For an authorized fix, use [processing](../wombat/references/processing.md). Keep the original task, issue and baseline for follow-up. Reproduce the affected behavior, check correctness after the edit, and compare later equivalent tasks only when available. Report these checks separately; a usage investigation does not create a configuration suggestion ID.
