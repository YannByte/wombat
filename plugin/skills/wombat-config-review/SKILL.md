# Configuration review and recheck

Read the [shared operating rules](../wombat/references/runtime.md) and [startup](../wombat/references/startup.md). Keep the requested project and configuration kinds. A configuration review does not require a whole-history usage scan.

Use [configuration queries](../wombat/references/configuration.md). Start with a small list, then read the selected findings and content. Keep inventory versions, suggestion identities and user-decision versions in their separate domains.

Explain each applicable issue using the exact file or section, the measured finding and a proposed change. Keep native discovery and parse observations separate from format reminders. Distinguish configured, loaded and successfully used resources. Missing use records cannot justify removal or disabling.

Preserve task triggers, required constraints and shared-project behavior when proposing shorter instructions. Review related scopes before editing shared configuration. Size estimates do not measure actual injected Tokens or prove savings.

If editing is authorized, follow [processing](../wombat/references/processing.md). Confirm the selected targets still match the reviewed versions. Edit only those targets. Recheck the original suggestion under the same rules. Keep user keep/not-applicable decisions separate from check results.

For a follow-up such as “check yesterday’s change,” retain the original issue and target. If they cannot be recovered reliably, ask for the missing selection. Do not choose a replacement from the current ranking.

Report the finding, any actual edit, the recheck result and remaining uncertainty. Static success does not prove historical loading, effective adoption, better task quality or savings. Use later version-bound observations and comparable usage windows only when available.
