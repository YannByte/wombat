# Apply selected improvements and verify

| Selected change | Execution | Verification |
|---|---|---|
| Code or workflow | Codex edits the actual owner using existing project mechanisms | Repeat the original case and relevant project tests, including a meaningful failure/recovery case |
| Configuration finding | Codex uses authorized native controls or the configuration owner | `check verify --baseline check.json --suggestion ID --json`, retaining all original roots/source/rule inputs |
| Skill or MCP choice | Apply only the selected native project/global change | Reinspect the same identity/scope and test capabilities the user still needs |
| Supported Codex cleanup | Guarded `clean --apply` with the original selected IDs | `clean verify` on that selection; inspect per-item outcomes |
| Project cleanup | Native tools on rechecked authorized exact paths | Recheck original candidates and retained deliverables without rebuilding every removed artifact |

Recover criteria from the user request and project instructions. Before editing, retain the original problem, target version, inputs and relevant check/baseline. Check current files and uncommitted work. Preserve unrelated edits; report-local numbers authorize only their displayed objects and effects. Reuse explicit authorization rather than asking again at every step.

Combine changes sharing a file and respect dependencies. Artifacts needed for tests are cleaned last. A failed step stops dependent operations; independent selected actions may continue. Report new findings without adding them to the selection. Cancellation stops subsequent work; already completed or uncertain actions remain explicit. Before retrying a write, inspect actual state instead of repeating the entire batch.

Configuration rechecks use the original roots, project/source filters and rule overrides. A comparable miss establishes only that check's absence; a hit remains. Missing or incomparable evidence cannot prove repair. Pass the original selected finding from the saved report; it does not depend on a running process. “Keep” and “not applicable” remain explicit user decisions, not repair results or automatic recheck changes.

For extension changes, retain exact path/identity, native state, project/source/date scope and estimate method. Reinspect current state with the same scope and a fresh inspection, comparing selected identities to the original saved result. Historical use counts do not reset after disabling. Restore only selected values without overwriting later unrelated edits. Workspace-wide resets and blanket cache deletion are not recovery.

Report each selected action: what changed, original-problem result, passed/failed/unrun/unavailable checks and retained material. Editing, build success or command exit alone does not verify behavior or user acceptance. Tests without an actual release do not establish publication success. Catalog reductions are estimates, not confirmed context savings.

Immediate repair and later improvement are distinct. Compare naturally occurring later work only with comparable scope, workload, methods and quality. Lower usage alone cannot establish causality. Do not create demonstration tasks, automatic adoption history, execution receipts or another tracking system. Save a report or decision only when requested.

## Try a Harness change on the same task

Use this workflow when the user asks to rerun a task under different project instructions or adopt or undo a version backed by a trial. Use ordinary diagnosis and rechecks for direct fixes that do not require a comparison.

1. Locate the chosen task using the existing history workflow. Read only the selected request and evidence. Confirm the current project, the behavior to fix, the behavior that must stay, and the files the trial can use. Use the current project instructions as the baseline. Explain any difference between the selected current files and the historical task.
2. Use `wombat system api harness --json` for the request schema. Pass the structured request to `wombat system call --json` using standard input. Create a `plan` with the absolute project path, a distilled task and explicit project-relative text file names. Do not include credentials, raw logs or unrelated files. Supply checks independently of the candidates. A `command` check observes the exact successful invocation in the Codex event stream. A `file` check compares an output path and its exact content. Wombat does not execute a check command on behalf of the trial. The selected files will be read-only in `../inputs` and the model writes to a private work directory.
3. Show the selected scope, checks, per-session time limit and six model sessions (four task runs and two editorial sessions) before starting. If `plan.globalInstructionSources` lists global instructions, explain they may be sent to the model and include them only with authorization for this trial. If already authorized, plan with `includeGlobalInstructions: true`. Run the confirmed plan with `run` and its `trialId`. Allow time for the four task runs. A host policy denial is a setup issue. Where Codex supports approval for a local command, request permission for this exact installed Wombat invocation and retain the trial's own restrictions. If the run is incomplete, report its failed stage and code, and review its status before planning another run. Preserve the host restrictions and the user's configuration.
4. Compare the four results and open the local report only when useful. Identify checks that changed, passed in both versions, or regressed. Show the difference between the original and composed project instructions. Keep the baseline if the recommendation is `keep_baseline`. Present the observed results without treating passing checks as assurance about other tasks.
5. When the user approves the reviewed version, call `apply` with the same `trialId` and `revision`. Then call `verify` with the trial ID to check the applied instructions in a fresh Codex session. Report write and load results separately. Call `undo` with the same trial ID and revision only when authorized. A version conflict requires review of the current file. Do not overwrite subsequent edits or widen the selection.
