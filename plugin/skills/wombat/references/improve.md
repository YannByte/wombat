# Improve a project workflow

Begin with an observed obstacle or the user's specific target. Use [diagnose](diagnose.md) for the three initial mechanism families: instruction and entry disagreement, checks bypassed by delivery, and failures without bounded handling or recovery.

Read the existing mechanism before proposing a new one. Prefer a correction to its owner, connecting an existing check or making a current failure path actionable. Do not add policy text, another Skill, a service or an overall scoring system by default.

For a configuration question, use [configuration](configuration.md) only when inventory, measured findings or historical loading is needed. Static file review does not require a usage scan. Size and missing use observations are review leads, not proof of a loading defect or wasted Tokens.

A proposed change must specify the affected task, observed consequence, exact file or command, preserved behavior and original case to rerun. Show evidence that weakens the proposal too. If no defect is established, stop with the missing deciding evidence.

When authorized, use [process and recheck](processing.md). Preserve the baseline and original success criterion. Report three separate outcomes: original issue checked, later adoption observed, and comparable later work improved. Unknown follow-up remains unknown. Never create consuming tasks just to claim adoption or savings.
