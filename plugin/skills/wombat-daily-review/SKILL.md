# Daily usage and improvement review

Read the [shared operating rules](../wombat/references/runtime.md). Reuse the selected executable, API information and adequate view. Use [startup](../wombat/references/startup.md) when these are missing or a runtime call fails.

Use the [bounded query flow](../wombat/references/query-flow.md). Keep the requested project, dates, timezone and model filters. For a daily review, state the day and timezone. Do not replace a requested period with all dates.

Batch totals and only the requested task or model rankings. Use the core summary; do not rescan source records to reproduce accounting unless the user requests an audit or the results conflict. A ranking page is not a complete population. Use [statistics](../wombat/references/statistics.md) only for distributions or workload comparisons.

For a work report, use [conversation evidence](../wombat/references/conversation.md). Locate and read only relevant work and delivery evidence at the same view. Give work labels alongside task IDs; one long conversation can contain several work items. Separate requests, recorded work and verified delivery. Do not infer unfinished work from missing completion records.

Read [investigation](../wombat/references/investigation.md) only when a selected signal needs it. Stop expanding the search when the requested supported findings are available. Keep required tests, failure recovery and accidental repetition distinct. If no actionable issue has evidence, say so; high usage alone is not a problem.

Give the period's usage, recorded work and the most useful changes. For each recommendation, name the affected step, the change and an observable check. An already fixed issue calls for a regression check, not another repair. Include costs only when useful or requested; keep unpriced usage separate. A report request does not schedule future runs.

For an authorized edit or later comparison, use [processing](../wombat/references/processing.md). Retain the original issue, scope and baseline. Check correctness first, then compare later equivalent work when available. Show changed workloads and missing follow-up data; lower usage alone does not prove improvement.
