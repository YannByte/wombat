# Daily usage and improvement review

Read the [shared operating rules](../wombat/references/runtime.md) and [startup](../wombat/references/startup.md). Reuse an adequate view and runtime discovery from this conversation.

Use the [bounded query flow](../wombat/references/query-flow.md). Keep the requested project, dates, timezone and model filters. For a daily review, state the day and timezone. Do not replace a requested period with all dates.

Start with totals and the task or model rankings needed for the question. Use [statistics](../wombat/references/statistics.md) when comparing task count and usage per task. Read [investigation](../wombat/references/investigation.md) only for relevant candidates. Select up to three useful findings unless the user requests another depth. Read the selected original evidence before proposing a change.

For each finding, connect the observed behavior, its source, one concrete change and a way to check the result. Check whether repeated commands were required tests or recovery steps. If no actionable finding has evidence, say so. High usage alone does not establish waste.

For a requested work report, use [conversation evidence](../wombat/references/conversation.md). Separate requests, recorded work and verified delivery. Use Git or other authorized delivery evidence when needed. Do not turn absent completion records into unfinished work.

Give the period’s usage first, then relevant changes and selected improvements. Include estimated costs only when useful or requested. Keep unpriced usage separate. A report request does not create a recurring task. If scheduling is requested, use the host’s scheduling capability.

For a later comparison, retain the original scope and metrics. Compare like periods and describe workload changes. Use [processing](../wombat/references/processing.md) for authorized changes and follow-up checks. Lower usage does not establish better quality or causal savings.
