# 决策记录：不可变快照与按需明细读取

中文 | [English](2026-09-30-snapshot-storage.en.md)

Status: implemented

旧格式兼容决定已由[未发布首版仅维护当前格式](2026-10-03-current-format-only.md)替代。

本记录从首版方案整理，记录日期为 2026-09-30，范围是显式保存的 v3 快照。当前 SQLite 实时索引与快照并存；其完整扩展目标见[实时用量提案](../../proposed/architecture/2026-09-30-live-usage.md)。

## 问题

单份全历史 JSON 使查询小范围明细也需要读取大量无关数据。刷新失败不能破坏上次结果；分页和下钻需要固定的版本、汇总及份额分母。旧快照还必须保留原身份、价格政策与缺失语义。

## 决定

- 使用不可变 generation：小 manifest、精简计量账本、按对话 JSONL 分片及轮次偏移/哈希。用量读账本，轮次读目标对话，步骤只读对应片段并校验。
- 刷新持有进程文件锁，在私有临时 generation 写完文件和哈希后提交 manifest，最后原子更新 latest。取消、失败和超限不发布半份快照；全部来源不可读时保留旧 latest。
- 查询固定 snapshotId，先对完整范围过滤、排序和汇总，再分页；份额分母不由已返回页面计算。无轮次关联的事实保留为未归轮记录。
- 只支持当前快照格式；原日志和恢复材料不属于索引清理范围。
- 仅保存白名单元数据，不保存消息、模型正文、完整命令参数或工具输出。源文件按本次读取边界处理，不把多文件读取声称为源头原子事务。

## 考虑过的方案

| 方案 | 取舍 |
|---|---|
| 继续使用单个大 JSON | 实现简单，但明细查询和重复解析随全量历史增长，不适合按需展开 |
| 首版立即引入数据库和常驻服务承担所有存储 | 增加部署、恢复和生命周期成本；先为显式快照建立固定结果与独立安装基线 |

后续自动同步确实引入 SQLite 和按需服务，因此第二项不是永久禁止数据库。实时索引承担增量状态，显式快照承担固定保存与可重复查询，两者职责见[当前架构](../../../development/architecture.md)。

## 影响与验证

需要维护分片、偏移、哈希、发布顺序及当前格式校验；文件数量增加，分页本身也不能保证计算量恒定。常规展开 p95 ≤300ms、冷查询 ≤1s 是目标，不能当成已经达到的性能。

[固定查询证据](../../../benchmarks/usage-v1-query-2026-09-30.json)包含 500 个对话、5,000 个轮次、10,000 条计量，11,000,000 Token / $28.35 在各层及全部分页守恒。测量包括进程启动、I/O、序列化和文本渲染；系统文件缓存未清空。取消、损坏、超限、旧身份和政策回归的范围见 Git 历史中的验证记录。更新此记录须核对 `core/src/usage_store.rs` 与存储/集成测试，不用历史耗时证明当前构建。
