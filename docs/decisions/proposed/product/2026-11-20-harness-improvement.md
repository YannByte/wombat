# 决策记录：Harness 改进的实施方案

中文 | [English](2026-11-20-harness-improvement.en.md)

Status: proposed

## 问题

Wombat 已能定位原始任务、检查配置并复查原问题。一次规则复查可以证明该规则的匹配结果发生变化。要判断某项 Harness 改动是否改善实际任务，还需要匹配条件的试跑、交付物和回归证据。用户需要能审阅、应用和撤销这项改动，并在下次遇到类似问题时复用经过验证的经验。

## 方案

将 Harness 改进作为 Wombat 的一项显式任务。面向已安装 Wombat 和 Codex 的用户，首版入口放在现有 Codex 对话中。用户选定一次失败或反复纠正的任务，确认使用的材料、要修复的行为、必须保留的行为和试跑预算。Wombat 返回产物对照和可应用的文件差异。用户可以保留原版或应用到当前项目。独立对比面板进入后续阶段，界面复用同一结果契约。

### 第一阶段：从历史任务到可撤销的改动

1. **准备试跑用例。** 用现有历史和配置查询定位原任务和目标文件。将任务要求、选定材料、当前配置和获准的未提交内容复制到私有快照，记录文件清单和内容指纹。固定实际执行的模型、推理设置、工具权限、运行环境和验证条件。历史配置只有在存在可靠版本证据时才可用于历史复现。材料不足时，允许用户选择当前材料，结果标明验证的是当前用例。
2. **先验证执行器。** 用合成任务在本机 Codex 中启动两个独立的临时会话。外层为每次执行从同一快照建立独立可写目录，生成一次性权限配置并准备所需工具。允许读本轮材料、运行本轮工具及写本轮产物，隔离原项目、其他轮次及用户配置和凭据。单独控制命令联网、网页、MCP、连接器和 Hook。模型服务连接由 Codex 宿主管理。先在 macOS arm64 验证已安装入口、现有登录复用和宿主启动方式，再按平台验收扩大支持范围。用户无需手写权限配置。预检确认不了执行边界时，试跑保持待处理并说明原因。参见 [Codex 权限方案](https://learn.chatgpt.com/docs/permissions)和[非交互执行](https://learn.chatgpt.com/docs/non-interactive-mode)。
3. **生成、试跑和组合。** 跑一次当前基础配置。以实际轨迹和交付物为依据，分别提出工作方法和领域规则两类候选。首版限定项目级说明、Skill 和可在本地验证的帮助脚本。每项候选声明目标行为及预期证据，校验文件和引用后分别运行。比较两份试跑和原版，组合有证据支持的改动，对组合版再运行一次。完整的单轮流程有四次任务执行，编辑和反思另计。原版未复现问题、输入漂移或证据不足时，给出相应状态。参见 [Harness² 第 2 节](https://arxiv.org/html/2610.14224#S2)。
4. **核对结果。** 逐项比较原问题、原有行为和产物可用性。字段、金额、测试结果等由独立检查判定，检查规则和预期值由外层持有，试跑只能提交待检查的结果。对需要判断的产物提供匿名对照和可定位证据。保留原版供用户比较。首个代码用例验证漏跑的测试步骤和正常路径，首个文件用例验证汇总口径、明细覆盖和实际生成的交付文件。
5. **应用和撤销。** 用户选择已验证的候选后，由 Codex 发起项目级应用。执行前核对目标和依赖的版本，冲突时保留候选并展示需要重新审阅的差异。写入后复查原问题，并在新会话检查目标配置是否实际加载。撤销前比较应用后版本和当前内容，保留用户后续改动。应用、加载和行为验证分别确认。

### 接口与状态

在现有 Skill 下交付试跑入口，CLI 与生成的非交互接口共享同一结构化状态。计划阶段返回选定范围、预计执行次数和缺失前提。执行阶段支持启动、查看状态和恢复，前台取消停止自有进程树。应用和撤销引用已验证的候选版本及原应用记录。Rust 管理试跑身份、版本校验和持久状态。TypeScript 宿主管理目录准备、有界子进程、输出收集和清理。Codex 负责编辑候选、判断行为差异以及发起获授权的项目修改。

第一个开发切片使用固定合成用例和预先给定的候选，先检验宿主执行。用例提供任务要求、只读材料清单、基础文件、候选差异和独立检查。每次运行返回完成状态、产物清单、检查结果和可定位的失败原因。文件复制与回收仅接收范围内的普通文件，拒绝越界路径和符号链接。验证执行器通过后，再把预设候选替换为 Codex 生成的候选，并接入组合、应用和撤销。将合成执行门槛接入现有验证入口。

已确认的试跑有自己的版本记录，绑定用例快照、实际 Harness、执行设置、检查方法和所用经验版本。阶段完成以产物验证和状态提交为准。中断后只复用依赖仍匹配、文件可核验的已完成阶段。结果缺失或工作区变化时，记录原因并重新安排受影响的阶段。并发启动只能有一个执行者取得同一阶段的执行权。应用和撤销绑定预期文件版本，并保留恢复部分写入所需的信息。

试跑在默认数据目录下独立保存。原始材料、完整轨迹和产物只在本地私有目录按试跑需要保留，用户可以选择保留交付物或清理试跑。长期记录保留必要的版本、结果和出处。模型调用通过宿主使用用户为试跑选定的材料。试跑用量按已有计量规则保留来源并去重。

### 实施顺序

1. **验证宿主启动。** 在 `client/src/node/codex/` 复用原生进程的取消、超时和输出限制，为试跑单独传入工作目录、权限和允许继承的环境变量。先做宿主支持性检查、可写副本和产物验证，再用已安装的插件运行两个真实 Codex 会话。用可控进程替身覆盖失败、取消和回收，用真实会话验证既有登录和权限生效。
2. **接入四次执行。** 在 `core/` 增加试跑状态与版本契约，从 Rust 生成 TypeScript 和 Schema。`cli/` 提供计划、启动、查看和恢复，主 Skill 复用现有历史与检查查询，并将选定材料、候选差异和独立检查交给执行器。按原版、工作方法候选、领域候选、组合版的顺序接通证据，先跑通两个合成用例。
3. **交付应用和撤销。** 在已有项目修改边界内加入带版本前提的写入和恢复，接通配置加载证据。在安装版上从普通对话跑完两个用例，用户能看到产物、各项检查、差异和应用结果。验证通过后再开放后续阶段的界面与经验反馈。

先验证现有会话能否启动独立受限会话。若外层会话边界阻止启动，验证 Codex 是否提供受支持的宿主启动方式，包括按宿主策略由用户确认一次启动。任一路径都要实测子会话的有效权限。宿主策略拒绝或没有受支持的启动方式时，当前安装环境不可试跑。

开发验证入口为 `corepack pnpm verify:harness-trial -- --codex-bin <绝对路径>`。它启动独立的 Codex 会话，逐个核对模型、权限和指令来源，再在通过预检的同一会话内用本机模拟服务驱动工具调用。验收要求匹配会话与轮次、边界检查通过并收回正确的产物。原版应重现错误结果，候选版应通过正确性检查。已登录会话中的模型调用和安装后的对话入口另行验收。

真实文件任务的开发入口为 `corepack pnpm harness:trial -- --manifest TASK.json --output DIRECTORY`。在 macOS arm64 上使用已登录的本机 Codex。清单提供任务、现行指令、同目录内明确选定的文本文件和可独立运行的文本检查。执行器固定同一个模型，分别收回原版、通用候选、领域候选和组合版的 Markdown 交付物。报告记录输入指纹、执行事件摘要、检查结果和组合理由。未选择的全局指令会阻止提交任务，确认参与的指令路径通过 `--allow-instruction` 单次选入。报告供审阅，候选直接应用、撤销和安装后的对话入口仍需验收。

启动会话时也要核对加载的指令。用合成全局 `AGENTS.md` 实测，`codex exec --ignore-user-config` 仍把全局指令送进模型请求。App Server 的 `thread/start` 可以在发送任务前返回 `instructionSources`，作为核对所选材料的预检入口。若宿主加载了未纳入试跑的指令，继续保持待处理。参见 [Codex App Server 会话接口](https://learn.chatgpt.com/docs/app-server)。

已安装入口的首个范围由 `harness` 结构化方法和现有 Wombat Skill 提供。使用项目根目录中现有的 `AGENTS.md`、选定的 UTF-8 文件以及明确的检查条件。命令检查使用真实会话中同一工作目录下的成功执行事件，文件检查读取隔离目录中的实际产物。应用和撤销绑定试跑的版本，加载检查启动新会话并核对指令来源。正常安装和真实模型试跑可用 `corepack pnpm verify:harness-installed` 验收。完整项目快照、多文件候选、试跑恢复、其他平台和经验库仍按各自条件验收。

### 第二阶段：项目 Harness 版本

提供项目级历史、对比预览、加载验证和选择性撤销。将会话中的试跑状态、候选差异和实际产物接入同一对比界面，先通过安装后的宿主验证界面能否承接这些操作。用自然发生的后续任务观察同类问题是否再现，保留对应的配置版本、证据和质量条件。跨项目及全局应用需要明确其影响范围。

### 第三阶段：让经验影响后续改进

反思覆盖原版、落选候选和组合版。只保留有证据支持的经验，记录触发条件、有效组件或可定位的版本、验证方式、反例和失效前提。按项目和任务条件检索少量适用条目，用来决定先查哪里、改什么、怎么验证。让后续改进记录说明哪条经验改变了哪个决定。用留出的新任务对照有无经验的效果，再决定是否更新候选或检查策略。

## 考虑过的方案

直接扩展现有 check 复查可以低成本修复可由规则判定的问题。受控试跑补充实际行为和回归证据，两种验证都应使用其对应的原条件。直接移植官方基准运行器可以复用研究流程，但会引入基准数据、运行器权限和实验目录约定。借鉴阶段和证据接口，使用已安装 Codex 的执行能力，能让产品控制用户授权的材料、环境和应用范围。参见[官方运行器的网络边界](https://github.com/google-research/harness2/blob/6868817518876de8fd170c6a8354daca273b6191/docs/EXPERIMENTS.md#web-access)。

本提案在交付后将部分取代[按需检查与单插件决定](../../implemented/architecture/2026-10-31-on-demand-checks.md)中的任务和持久记录边界，范围限于用户主动发起的试跑、应用与撤销。普通观察、历史查询和只读复查继续遵循该决定。[优化生命周期提案](2026-10-03-optimization-lifecycle.md)仍负责自然任务中的采用与收益证据。受控试跑提供当前用例的对照证据，自然后续任务用于判断实际采用和持续效果。

## 验收条件

- **执行器门槛。** 在首次安装的目标平台，从正常入口启动真实 Codex 会话，复用已有登录并在两个副本中写出可读取的产物。用合成文件检查数据和临时目录隔离、原项目和兄弟工作区访问限制、未经授权的工具访问、超时取消和清理。运行前预检抛出可理解的错误。
- **第一阶段。** 代码和文件用例均从定位原问题走到四次执行、候选对照、应用、加载检查和撤销。覆盖改善、回归、原版未复现、部分失败和恢复。用独立预期核对实际产物。改变输入或配置时，旧证据失效。
- **第二阶段。** 用户能独立选中版本、打开对比、确认应用并撤销。重复请求不重复应用，并发修改不会被覆盖。区分写入、实际加载和后续任务观察。
- **第三阶段。** 用同等条件的新任务对照有无经验时的诊断、候选和验证选择，同时检查任务质量、回归及新增成本。至少覆盖一个适用案例和一个前提不符的反例。自然任务的改善需要独立的后续证据。
