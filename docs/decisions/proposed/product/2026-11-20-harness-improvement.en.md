# Decision Note: Harness improvement implementation plan

[中文](2026-11-20-harness-improvement.md) | English

Status: proposed

## Problem

Wombat can locate the original task, inspect configuration, and recheck the original problem. A rule recheck can establish a change in that rule's outcome. To determine whether a Harness change improves a task, users need runs under matching conditions, actual deliverables, and regression evidence. They also need to review, apply, and undo the change, and to reuse verified lessons when a similar problem occurs.

## Proposal

Make Harness improvement an explicit Wombat task. The first release starts in the existing Codex conversation for users who have Wombat and Codex installed. The user selects a task that failed or needed repeated correction, then confirms the materials, the behavior to fix, the behavior to preserve, and the run budget. Wombat returns a deliverable comparison and a file diff the user can apply. The user can keep the original version or apply the change to the current project. Add a dedicated comparison view in a later phase using the same result contract.

### Phase one: from a previous task to a reversible change

1. **Prepare the test case.** Use existing history and configuration queries to locate the original task and target files. Copy the task request, selected materials, current configuration, and authorized uncommitted changes to a private snapshot. Record a file inventory and content fingerprints. Fix the execution model, reasoning settings, tool permissions, runtime, and acceptance conditions. Reproduce historical configuration only when reliable evidence identifies its version. When materials are missing, let the user select current materials and identify the current case in the result.
2. **Qualify the runner first.** Start two independent ephemeral sessions in local Codex using a synthetic task. A host process creates a separate writable directory from the same snapshot for each run, generates a temporary permission profile, and prepares the tools. Allow access to the run's inputs, tools, and outputs. Isolate the original project, other runs, and user configuration and credentials. Control command networking, web, MCP, connectors, and hooks separately. The Codex host manages its model connection. On macOS arm64, first qualify the installed entry, reuse of the existing sign-in, and host launch path, then qualify each additional platform. Users do not need to write permission settings. If preflight cannot establish the execution boundary, keep the run pending and show the reason. See [Codex permission profiles](https://learn.chatgpt.com/docs/permissions) and [non-interactive execution](https://learn.chatgpt.com/docs/non-interactive-mode).
3. **Propose, run, and compose.** Run the current base configuration once. Use the actual trajectory and deliverable to propose one workflow candidate and one domain candidate. Limit the first release to project instructions, Skills, and helper scripts that can be checked locally. Each candidate states its target behavior and expected evidence. Validate files and references, then run the candidates separately. Compare both runs with the base, compose the changes supported by evidence, and run the composition again. One full round has four task runs, with separate editing and reflection sessions. Report when the base does not reproduce the issue, inputs drift, or evidence is insufficient. See [Harness² section 2](https://arxiv.org/html/2610.14224#S2).
4. **Check the results.** Compare the original issue, existing behavior, and deliverable usability one criterion at a time. Use independent checks for fields, amounts, test results, and other directly observable results. The outer process holds the checks and expected values, and the trial submits results for evaluation. For outputs that require judgment, provide a blind comparison and evidence the user can locate. Keep the base output available for comparison. The first code case checks a missed test step and the normal path. The first file case checks aggregation rules, row coverage, and the generated deliverable.
5. **Apply and undo.** After the user selects a verified candidate, Codex requests application at project scope. Check target and dependency versions before writing. On conflict, retain the candidate and show the diff that needs review. After writing, recheck the original issue and use a new session to verify that the target configuration loads. Before undo, compare the applied version with the current files and preserve later user edits. Confirm writing, loading, and behavior separately.

### Interfaces and state

Deliver the trial entry through the existing Skill. The CLI and generated non-interactive interface share structured state. Planning returns the selected scope, estimated run count, and missing prerequisites. Execution supports start, status, and resume. Foreground cancellation stops the process tree owned by the runner. Apply and undo reference the verified candidate version and original application record. Rust owns trial identity, version checks, and durable state. The TypeScript host owns directory preparation, bounded subprocesses, output collection, and cleanup. Codex edits candidates, judges behavior changes, and initiates authorized project updates.

The first development slice uses a fixed synthetic case and a predefined candidate to qualify execution in the host. The case supplies the task request, a read-only material inventory, base files, a candidate diff, and independent checks. Each run returns a completion status, an artifact inventory, check results, and a failure reason that identifies the affected stage. Copy and collect only regular files within scope. Reject paths outside the boundary and symbolic links. After the runner passes, use candidates generated by Codex and add composition, application, and undo. Integrate the synthetic execution gate with the existing verification entry.

A confirmed trial has a version record that binds the case snapshot, effective Harness, execution settings, check method, and experience version used. A stage completes after artifact validation and state commit. After interruption, reuse only completed stages whose dependencies still match and files remain verifiable. If a result disappears or a workspace changes, record the reason and schedule the affected stages again. Only one concurrent caller may take ownership of the same stage. Apply and undo use expected file versions and retain the information needed to recover a partial write.

Keep trial data separate under the default data directory. Keep original materials, full trajectories, and deliverables in a private local directory for the duration needed by the trial. Users can retain deliverables or clean up the trial. Long-term records keep the necessary versions, results, and provenance. The host sends materials selected for the trial to the model service. Use existing measurement rules to retain usage provenance and deduplicate records.

### Implementation order

1. **Qualify host launch.** Reuse native process cancellation, timeouts, and output limits in `client/src/node/codex/`. Explicitly supply the trial working directory, permissions, and allowed inherited environment variables. Add host preflight, writable copies, and artifact validation, then run two actual Codex sessions through the installed plugin. Use a controlled process substitute to cover failures, cancellation, and cleanup. Use actual sessions to verify existing sign-in and applied permissions.
2. **Wire up the four runs.** Add trial state and version contracts in `core/`, then generate TypeScript and Schema from Rust. Expose plan, start, status, and resume in `cli/`. The main Skill reuses existing history and check queries, then passes selected materials, candidate diffs, and independent checks to the runner. Connect evidence for the base, workflow candidate, domain candidate, and composition, then run both synthetic end-to-end cases.
3. **Deliver apply and undo.** Add version-conditional writes and recovery within the existing project edit boundary, then connect configuration load evidence. Run both cases through an ordinary conversation in an installed copy. Users can see the artifacts, each check, the diff, and the application result. Qualify that flow before opening the later comparison and experience features.

First test whether the current session can start an independent restricted session. If the outer session's boundary prevents startup, test a supported Codex host launch path, including one user confirmation for launch when required by host policy. Verify the child session's effective permissions on either path. If host policy denies launch or no supported path exists, the installation cannot run trials.

Use `corepack pnpm verify:harness-trial -- --codex-bin <absolute-path>` for development verification. It starts independent Codex sessions, checks their model, permissions, and instruction sources, then drives tool calls through a local synthetic provider in each validated session. Acceptance requires matching session and turn identities, passing boundary checks, and collecting the expected artifacts. The base should reproduce the incorrect result, and the candidate should pass the correctness check. Model calls using existing sign-in and the installed conversation entry have separate acceptance checks.

Use `corepack pnpm harness:trial -- --manifest TASK.json --output DIRECTORY` to run a real document task during development. On macOS arm64 it uses the local Codex sign-in. The manifest supplies the task, current instructions, explicitly selected text files from the same directory, and independent text checks. The runner uses one fixed model and collects Markdown deliverables for the base, general candidate, domain candidate, and composed version. The report records input fingerprints, a summary of execution events, check outcomes, and composition rationale. Unselected global instructions block submission. Use `--allow-instruction` to include a confirmed instruction path for this trial. The report supports review. Applying or undoing a candidate and the installed conversation entry have separate acceptance checks.

Check loaded instructions at session startup as well. A test with a synthetic global `AGENTS.md` showed that `codex exec --ignore-user-config` still included those instructions in the model request. App Server `thread/start` can return `instructionSources` before submitting the task, providing a preflight for the selected materials. Keep the run pending when the host loads instructions outside the trial scope. See the [Codex App Server thread interface](https://learn.chatgpt.com/docs/app-server).

The first installed entry uses the structured `harness` method and the existing Wombat Skill. It uses the existing root `AGENTS.md`, selected UTF-8 files, and explicit checks. A command check uses a successful execution event in the same workspace of the real session. A file check reads the actual output in the isolated workspace. Application and undo use the trial revision. A fresh session checks the instruction source. Use `corepack pnpm verify:harness-installed` to exercise installation and the real-model comparison. Full project snapshots, multi-file candidates, trial recovery, other platforms, and the experience library have separate acceptance criteria.

### Phase two: project Harness versions

Provide project history, comparison previews, load checks, and selective undo. Bring trial status, candidate differences, and actual deliverables into one comparison view. Test whether the installed host can support these actions. Use subsequent natural tasks to observe whether similar problems recur, with the corresponding configuration version, evidence, and quality conditions. Show the affected scope before applying changes across projects or globally.

### Phase three: use experience in later improvements

Reflect on the base run, rejected candidates, and the composed version. Keep only lessons supported by evidence. Each entry records the trigger, effective component or identifiable version, verification method, counterexamples, and invalidation conditions. Retrieve a few applicable entries by project and task conditions to inform what to inspect, what to change, and how to verify it. Record which lesson changed a later decision. Compare effects on held-out tasks with and without experience before updating proposal or verification strategies.

## Alternatives considered

Extending the existing check and recheck flow is inexpensive for issues with a deterministic rule. Controlled trials add behavior and regression evidence. Use the original conditions that apply to each check. Porting the official benchmark runner would reuse the research flow and bring in benchmark data, runner permissions, and experiment directory conventions. Reuse the stage and evidence boundaries with the installed Codex execution capabilities so the product can control authorized materials, execution settings, and application scope. See the [official runner network boundary](https://github.com/google-research/harness2/blob/6868817518876de8fd170c6a8354daca273b6191/docs/EXPERIMENTS.md#web-access).

On delivery, this proposal will partially supersede the task and durable record boundaries in [on-demand checks and one plugin](../../implemented/architecture/2026-10-31-on-demand-checks.en.md) for user-initiated trials, application, and undo. Ordinary observation, history queries, and read-only rechecks continue under that decision. The [optimization lifecycle proposal](2026-10-03-optimization-lifecycle.en.md) retains ownership of adoption and benefit evidence from natural tasks. Controlled trials provide comparative evidence for the current case. Later natural tasks support conclusions about adoption and sustained effects.

## Acceptance criteria

- **Runner gate.** On a clean installation of the target platform, start actual Codex sessions from the normal entry, reuse the existing sign-in, and write readable deliverables in both copies. Use synthetic files to verify isolation of data and temporary directories, restrictions on the original project and sibling workspaces, unauthorized tool access, timeouts, cancellation, and cleanup. Preflight reports an actionable error before execution.
- **Phase one.** Both the code and file cases go from original problem to four runs, candidate comparison, application, load check, and undo. Cover improvement, regression, no reproduction, partial failure, and resume. Check actual deliverables against independent expectations. Input or configuration changes invalidate prior evidence.
- **Phase two.** A user can select a version, open the comparison, confirm application, and undo independently. Repeated requests apply the change once. Concurrent edits are preserved. The product distinguishes writing, loading, and observations from later tasks.
- **Phase three.** Use new cases under matching conditions to compare diagnosis, candidate choice, and validation with and without experience. Also check task quality, regressions, and added cost. Include at least one applicable case and one counterexample with different prerequisites. Improvement in natural tasks requires separate follow-up evidence.
