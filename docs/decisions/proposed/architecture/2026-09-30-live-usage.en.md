# Proposal: persistent live-index views and scale targets

[中文](2026-09-30-live-usage.md) | English

Status: proposed

This page owns unfinished storage reduction, persistent MVCC, dependency-closure reconciliation, database aggregation, and scale acceptance. The [live-query](../../implemented/architecture/2026-10-01-rust-live-query.en.md) and [compact-index](../../implemented/architecture/2026-10-02-compact-live-index.en.md) decisions cover delivered on-demand services, incremental cursors, SQLite transactions, and fixed in-memory views. The [core](../../../reference/core.en.md), [contract](../../../development/contracts.en.md), and [CLI guide](../../../guides/cli.en.md) own current operations and lifecycle without repetition here. Retired TUI behavior, old-protocol compatibility, and old-snapshot migration are no longer proposed.

## Problem

Source-wide candidate reconciliation and in-memory facts still grow with history. Retaining fixed views in memory is not persistent MVCC. Incremental reading alone does not make reconciliation, queries, or memory proportional to additions. Narrow affected computation while retaining late evidence, corrections, retractions, and hierarchical conservation.

The live database stores safe observations, parser projections, query membership, and access indexes. It is more than a set of file offsets. Event envelopes repeat source, generation, task, turn, time, and identity fields. Equal projections share payloads, but per-event membership still repeats identifiers. Parser restoration replays events while stored projections also serve reads. These have different purposes; removing either representation requires replacing its consumers. SQLite JSONB reduces encoding overhead but does not remove repeated facts or fields. The [SQLite JSONB reference](https://www.sqlite.org/json1.html#jsonb) describes a modest space reduction and linear complexity for most operations. Local size observations belong in private test artifacts, not public fixtures.

## Proposal

### Computational model

Treat this as exact incremental maintenance of a local analytical database. At committed revision `v`, let `E_v` be the retained safe observations with physical identities; `D_v` the explicit identity and inheritance dependencies; `F_v = R(E_v, D_v)` the canonical measurements and operations produced by Rust reconciliation; and `A_v(q) = Q_q(F_v, price_v)` the result for a query scope. Evidence queries additionally read a selected subset of `E_v`. Missing source files change availability and coverage; they do not imply negative accounting contributions.

These relations have different access patterns. Persist observations in independently readable cold blocks. Persist canonical facts and contribution provenance as compact typed records. Persist only demonstrated aggregate keys, with revision and price ownership. Keep parser checkpoints and a byte-bounded working set in memory. Aggregate queries must not open observation blocks, and restoring a committed query view must not call the full event replay path. Exact analysis can still decode selected cold evidence under its existing limits.

An update produces `deltaF = removed(-1) + inserted(+1)` after reconciliation of the dependency closure `C(deltaE)`. For an additive aggregate, `A_(v+1) = A_v + fold(deltaF)`. The negative weight belongs to the maintenance relation, not to a negative public token measurement. For example, replacing a synthetic cumulative estimate of 120 tokens with exact measurements of 40 and 70 tokens retracts 120 and adds 110; adding the new measurements alone would report 230. Persist the old contribution or recover it through an indexed provenance relation. Changes to model state, cumulative intervals, explicit ancestry, or aliases can enlarge the closure. A small input change does not prove a small closure.

Classify each reduction before incrementalizing it. Token and exact decimal subtotals support signed deltas. Missing counts, unpriced counts, and known subtotals are separate components, so null never becomes zero. Minimum/maximum values, exact distinct sets, conflict witnesses, interval unions, and connected components need auxiliary state or affected-group recomputation after removals. Retaining only a previous scalar, top-k list, or two conflict witnesses is insufficient for general deletion. Physical-record counts must remain separate from canonical operation counts. Local-day queries require exact timezone boundaries and original timestamps; UTC daily totals cannot answer arbitrary local days.

Keep two dependency graphs separate. Typed Call/Item aliases form undirected components only within the exact source/thread/turn scope. Explicit inheritance supplies directed dependencies across those scopes. An internal component root is not a public stable operation ID: source-anchor ordering and collision resolution remain independent rules. Cycles, missing identity, and uncertain ancestry keep their current failure or coverage semantics.

Let `N` be total observations, `Delta` changed observations, `C` their reconciliation closure, `M` the memory budget, `W` worker count, and `P` a worker's admitted partition bytes. The target is `peak <= fixed_state + caches + queues + W*P <= M`, including database pages and codec buffers. Store larger state on disk; do not hide it in memory-mapped pages or a second process. Partitioning alone is insufficient because one task can contain most observations. Use spillable intermediate runs and bounded merges, or fail without changing the committed view if the admitted input cannot be processed. New work is proportional to reading `Delta`, resolving `C`, and maintaining its indexes, rather than routinely replaying `N`. Full rebuild still reads all required source bytes; bounded memory cannot remove that lower bound or the cost of required integrity checks.

### Business value and retention

Prefer an aggregate-oriented index with compact exact facts and source-backed detail. Do not copy every safe event into permanent storage merely because the parser emits it. Preserve historical accounting and define which analysis remains available without sources before changing storage. A date filter narrows the answer; it does not authorize deleting older facts.

| Data | Business requirement | Proposed treatment |
|---|---|---|
| Canonical measurements and accounting inputs | Exact totals, arbitrary dates/timezones, models, tasks, inheritance, corrections, and repricing | Persist compact typed facts and the observation evidence needed to recompute them; no automatic age-based deletion |
| Canonical operations and associations | Historical failures, durations, resources, repeated requests, Skill/MCP use, and work | Persist the required fields and aliases once; retain conflicts and observation provenance; never assign operation costs |
| Safe event evidence | Timing, first-content delay, physical-record counts, gaps, context boundaries, and evidence pages | Persist exact compact observations needed by these calculations; resolve remaining detail from verified source ranges, with bounded caches; pin required offline evidence in compressed blocks |
| Source identity, generations, checkpoints, and coverage | Correct incremental reads, replay, missing sources, and source changes | Persist independently of disposable query caches; preserve precision and unknown states |
| Totals, rankings, analysis results, and decoded blocks | Fast answers for a fixed scope and version | Persist frequently used small aggregates; bound optional caches; update affected aggregates atomically with facts and keep decoded detail disposable |
| User decisions, handling history, and explicit snapshots | Durable user intent and fixed evidence | Keep outside index eviction and rebuild; account for their space separately |

Audit every persisted field against a current query, accounting rule, replay requirement, or evidence contract. Remove a field only after all consumers and failure paths have a replacement. Do not retain speculative fields for future features. Do not merge distinct physical records because their values match: message counts, operation phases, ordering, and coverage can depend on those records. Exact replay deduplication keeps its current identity rules. Raw conversation bodies, arguments, and tool output remain excluded.

Use three tiers: small hot aggregates, compact exact facts and source locators, and on-demand detail. Cold means a different access and retention policy, not a second full copy hidden outside the database. The original read-only logs are the source tier; newly created archives and persistent caches count toward index footprint. Retain only evidence required for exact recomputation or promised offline capabilities, plus evidence pinned by user history and fixed snapshots. A full offline evidence archive remains an explicit alternative to measure, not a prerequisite for every installation.

Source-backed detail changes offline guarantees: source deletion, replacement, or unreadability can make old details unavailable while retained accounting remains readable. Expose those capabilities and coverage in Web and non-TTY interfaces. A locator needs source identity, generation, byte range, parser version, and the minimal context required for independent parsing. Verify the range and required context; file length and modification time alone do not prove unchanged content. Source mismatch must not return detail from the wrong revision. Test first access with no derived cache, source mutation/removal, and cross-range context. A complete cold-detail request remains subject to the 100 ms gate; an acknowledgement is insufficient. Do not silently evict already promised offline evidence during a rebuild.

### Compact facts and evidence

Keep the Rust domain boundary; storage engines and algorithms remain open choices. SQLite is the comparison baseline, not a required final engine. Use typed tables for queried measurements, operations, source generations, tasks, turns, and their relationships. Store repeated paths and identities through shared dictionary keys. Keep public stable identities unchanged; use local integer keys for joins and full binary hashes where hashes must persist. Do not truncate hashes or replace durable identities with installation-local row numbers. Typed timestamps preserve original precision and missing values; do not round nanoseconds to milliseconds. Preserve exact token integers, decimal amounts, conflicts, and distinct unavailable reasons.

Store each retained immutable observation payload once. Canonical facts are deliberate query projections, with links to the observations that establish them. Shared payloads must not point at mutable canonical rows that later corrections can change. Remove redundant parser copies only after replacing projection references and proving restart reconstruction. Replace per-event projection membership with source-generation or block membership when membership is identical; represent actual exceptions explicitly. Index compact task/turn/time keys for demonstrated query paths. Compare ordinary rowid and WITHOUT ROWID tables for each row shape instead of applying one table form everywhere; [SQLite documents different tradeoffs](https://www.sqlite.org/withoutrowid.html).

Store retained offline safe evidence in independently decodable blocks. The SQLite candidate keeps blocks in BLOBs so metadata and blocks use the same transaction. Other candidates must provide equivalent atomic publication and recovery. External immutable files require durable staging, an atomic committed manifest, and reader-aware orphan reclamation; renaming files alone does not establish a cross-store transaction. Group blocks by source generation and task/turn locality, with explicit partitions for unattributed evidence. Shared block metadata removes repeated envelopes; bounded dictionaries encode repeated strings. Benchmark established serialization and [Zstandard](https://facebook.github.io/zstd/) libraries instead of designing a compression codec. Start with low compression levels and 128–512 KiB target decoded blocks; these are experiment parameters, not delivered limits. Preserve the existing oversized-record contract and bound complete decoded size, dictionaries, checksums, and cancellation work before allocation. Compression must reconstruct the same safe event values, identities, provenance, precision, and source order.

Keep a bounded mutable tail and seal completed blocks. Late observations append new facts and invalidate affected projections; they do not rewrite a whole task archive or all history. Queries locate task/turn blocks through a small directory. Decode only selected blocks into a bounded cache. Hashes, format versions, declared sizes, and actual decoded sizes must agree. Never use source logs as the only copy of retained offline evidence. A new block format and storage layout have their own versions; a lossless encoding change alone does not change accounting methods or public DTOs.

### Query cost and storage lifecycle

The committed query header, bounded same-revision query batch, explicit generation rebuild, and recent-file preparation now use the [core](../../../reference/core.en.md) and [CLI](../../../reference/cli.en.md) paths. These changes separate answering a usage question from recovering parser state. Repeated polling and synthetic project restoration batches add work without establishing source progress, so they are removed. Recent preparation includes complete declared fork/copy families because older evidence can change recent accounting. Its deferred coverage remains provisional; modification time cannot prove complete coverage for an event-date range. Full parser residency, complete-request latency, rebuild space previews and obsolete-generation reclamation remain unfinished acceptance.

Persist only a small set of demonstrated aggregates, such as complete task totals and selected calendar summaries. Do not materialize the Cartesian product of all projects, models, time ranges, and timezones. Keep exact timestamped facts for arbitrary filters and local-day boundaries. Missing, zero, partial, and unpriced remain separate in aggregates. Corrections must retract the prior contribution and publish the replacement in the same revision; cache expiry alone cannot repair stale accounting.

Usage totals, daily distributions, and task rankings read canonical facts and suitable aggregates without restoring all safe events. Analysis reads the required operation slice and evidence blocks. Query planning must account for selected timezones and unsupported aggregate combinations rather than using incorrect subtotals. Stream scans and reductions; avoid materializing all facts before pagination. Restart restores only required checkpoints and query state, then loads detail on demand. Track database pages, decoded caches, parser state, and the full process tree separately. The disk reduction does not count as complete if startup still retains every event in memory.

Limit derived caches by bytes and entries. Bound read-view leases and release unreferenced fact versions and blocks after readers expire. Routine cleanup must retain current facts, referenced evidence, user records, and fixed snapshots. Report retained facts, disposable caches, WAL, free pages, and obsolete generations separately. SQLite [WAL checkpointing](https://www.sqlite.org/wal.html) and journal retention settings do not provide a hard disk quota. Check available space before staging work, bound transactions and temporary sorting, and stop with the last committed view when capacity is insufficient. A stopped scan reports incomplete coverage; it never reports zero usage or silently trims history.

Provide an explicit, scope-bound rebuild flow through Web and non-TTY entries. Preview affected index data, source availability, preserved user records, and estimated peak space. Unknown formats remain rejected and preserved; rebuilding from sources is not an in-place compatibility migration. Build a new generation, validate it, then switch atomically. Retain the old generation until successful replacement and authorized retirement; do not accumulate generations without an exposed reason and cleanup action. Include old plus new databases, WAL, and temporary files in the space estimate. Missing sources prevent a claim of full historical recovery. This flow must resolve an unsupported-format dead end without requiring manual database deletion.

### Dependency reconciliation and atomic commits

Retain file contributions, cross-file candidates, and dependencies; reconcile affected threads and cumulative intervals with insertions, corrections, and retractions. Modern detail can retract cumulative adjustments, inherited ownership can correct copies, and tool results update original operations. Unknown closures fall back to source-wide rebuilding with visible synchronization rather than adding new-line totals.

Parser checkpoints retain allowlisted state including model/effort inheritance, previous cumulative values, and unfinished call associations, without raw messages or tool output. Cursors are not complete state. File identity, length, and boundary hashes cannot prove an unchanged prefix; appends with earlier rewrites need budgeted full verification and explicit watermarks, without promising discovery of arbitrary edits within two seconds.

Commit candidates, canonical facts, prices, aggregates, source state, parser checkpoints, offsets, and revision atomically. Large rebuilds may stage chunks but switch generations once, keeping readers on the preceding committed view. Precommit crashes reread; postcommit recovery is idempotent. Missing or unreadable sources never silently erase accounting. Publish change notifications only after commit.

### Persistent views and database aggregation

The SQLite candidate uses versioned facts and stable identities with validFrom/validTo visibility. Other engines must demonstrate the same durable revision and visibility contract; an engine snapshot API alone is insufficient. A readView pins index instance, revision, price epoch, and lease. Queries use short transactions instead of long WAL readers that block checkpointing. Pagination, totals, and drill-down share a version; expiration fails explicitly rather than switching. Bound leases, GC, and backpressure without reclaiming referenced facts, fixed snapshots, or irreplaceable user decisions.

For the SQLite candidate, WAL, FULL synchronization, and one writer reuse database transactions. Alternative engines must retain equivalent committed-data durability and one core-owned publication boundary. Network shares are not supported local-database deployments. Database corruption requires isolation and an independently designed rebuild flow without deleting sources, identity registrations, or user decisions. Unreleased versions maintain only current formats and reject unknown versions while preserving data, following the [current-format decision](../../implemented/architecture/2026-10-03-current-format-only.en.md).

Store money as canonical decimal strings or explicitly scaled integers, never REAL sums. Time, source, model, project, and thread indexes support pre-pagination totals. Cache keys include scope, timezone and rule version, price epoch, and revision. Arbitrary local days cannot be assembled from UTC daily subtotals. Unknown classifications retain counts and known subtotals; corrections recompute affected buckets without subtracting null as zero.

Price acquisition follows the [current pricing policy](../../../reference/pricing.en.md). Build new price projections from canonical facts and switch atomically after completion. Views never mix rates and fixed-snapshot amounts do not follow index updates. Distinguish fact changes from price revisions in notifications, coalesce invalidation for slow clients, and explicitly require requery after overflow or reconnect rather than promising complete replay.

## Alternatives considered

Frequent full refreshes reread and rewrite history; adding new bytes alone cannot handle inheritance, cumulative corrections, or truncation. Independent watchers per entry duplicate collection and complicate writer locks and lifecycle. Permanent daemons add installation and residency costs, so the on-demand shared service remains the boundary. Memory-only state loses recovery checkpoints, while repeated full JSON exports grow with history. Fixed snapshots remain explicit archives and incremental indexes serve live queries.

VACUUM and page-size tuning can reduce unused space but cannot remove retained event payloads. Compressing each current row keeps duplicate identifiers and pays codec overhead per row. Compressing one whole database or task archive makes small appends and detail reads expensive. Keeping only daily totals loses arbitrary filters, corrections, and evidence. Dropping all events breaks existing timing and historical-use capabilities. Replacing SQLite is permitted when measured end-to-end benefits justify its transaction, integration, and packaging costs. Engine choice does not remove the need to eliminate duplicated business representations. The preferred sequence is a field-level retention audit, compact exact facts and aggregates, verified source-backed detail, and bounded compressed blocks for retained offline evidence. The source-backed and full-offline profiles require separate capability contracts and measurements. This proposal does not mark the implemented compact-index decision as replaced before the new layout passes acceptance.

### Storage and algorithm selection

Compare two primary prototypes first: compact SQLite tables with compressed evidence, and embedded DuckDB typed tables with its native column storage. Initial layout experiments may use schema-shaped synthetic rows, clearly labeled as storage-only evidence. Integration acceptance must use the same Rust-produced canonical facts and independent oracle so a parser change cannot masquerade as a storage improvement. Add a partitioned Parquet evidence variant if retained cold evidence remains a bottleneck after the primary prototypes. Evaluate RocksDB only if measured incremental writes or point/range reads remain a bottleneck. This order limits prototype cost without reserving the final choice for SQLite.

| Candidate | Question to test | Required checks |
|---|---|---|
| Compact SQLite plus compressed blocks | Can compact keys, shared facts, selective indexes, and evidence blocks meet both hard gates? | Aggregate scans, cold detail reads, WAL peaks, and index maintenance |
| Embedded DuckDB | Can column storage and analytical execution improve complete-history filters and aggregates within the storage budget? | Small corrections, selective detail reads, startup/RSS, index costs, and process ownership |
| Parquet cold evidence plus a transactional catalog | Can column encoding and partition pruning reduce retained evidence without slowing exact-task reads? | Row-group read amplification, tiny partitions, rewrite peaks, and atomic publication across files |
| RocksDB | Do ordered keys and write batches outperform the SQL candidates for demonstrated hot paths? | Secondary-index/aggregate implementation cost, compaction peaks, read amplification, and durable revision semantics |

DuckDB's [concurrency model](https://duckdb.org/docs/current/connect/concurrency) requires attention to the writer process; keep database ownership in the shared core service. Its [index guidance](https://duckdb.org/docs/current/guides/performance/indexing) distinguishes selective lookup benefits from aggregation and index-memory costs. [Parquet row-group guidance](https://duckdb.org/docs/current/data/parquet/tips) shows a tradeoff between selective reads and broad scans; a compact file alone does not prove 100 ms detail queries. The [RocksDB overview](https://github.com/facebook/rocksdb/wiki/RocksDB-Overview) describes ordered key/value access, atomic batches, and compaction; its snapshots do not persist across restarts. These documents identify experiments, not a winning engine.

Compare dictionary encoding for repeated strings, lossless delta encoding for ordered positions/times, RLE/bit-packing for low-cardinality values, and block compression through maintained libraries. [Parquet's encoding specification](https://parquet.apache.org/docs/file-format/data-pages/encodings/) provides established implementations to evaluate. Retain precision, nullability, provenance, and a recoverable source order even when physical rows are reordered for pruning. Compare vectorized aggregates and predicate/column pushdown with indexed row access; use bounded top-k selection when only k ordered results are needed, while computing full-scope totals separately. Bloom filters or probabilistic structures may skip work but must never decide accounting identity, exact counts, or deletion. Approximate cardinality or quantiles cannot replace existing exact results to satisfy latency.

A preliminary prototype choice is conditional. Adopt a production candidate only after it passes correctness, tenfold total-storage reduction, complete-request latency, and recovery gates on the same fixture. Among passing candidates compare peak memory, append/compaction writes, temporary space, executable size, startup, Rust integration, licensing, maintained bindings, offline operation, and all release targets. Pin dependency versions and run license checks before adoption. A hybrid layout must outperform its added publication and cleanup complexity. Keep money, attribution, and evidence semantics in Rust; SQL and codecs execute those rules rather than defining a second implementation. Record the measured choice and rejected alternatives before integrating a production writer; do not maintain several production storage backends without an actual consumer.

### Remove work before changing algorithms

Start with the current SQLite implementation and remove work that has no required consumer. A new engine, generic incremental runtime, additional worker or cache is justified only by a measured bottleneck that remains after this subtraction. The techniques below are alternatives for remaining work, not a list of components to implement.

| Work to remove | Required replacement and boundary |
|---|---|
| Restoring all observation blocks to answer statistics or open an unchanged committed view | Read persisted canonical facts and applicable aggregates. Decode evidence only for a consumer that needs it; retain required offline evidence |
| Rebuilding indexes and summaries for previously restored projects after each new project batch | Reuse completed partitions and their summaries; compute the incoming partition and changed cross-partition dependencies only. Preserve consistent partial-view coverage |
| Recomputing every historical group for an ordinary append | Replace contributions in the affected dependency closure. A price change updates prices and monetary aggregates, not source parsing or raw Token facts; wider identity corrections can require wider work |
| Preparing every analysis and dimension combination before any request | Keep only demonstrated common aggregates; calculate bounded detail results on demand. Deferred requests must still meet their own complete-response latency gate |
| Repeated passes, sorting and intermediate copies over the same selected facts | Fuse compatible reductions and reuse an established order when the consumer permits it. Preserve checked arithmetic, validation failures, stable identity and output ordering |

Verify subtraction with work counts as well as elapsed time: decoded observation records, facts visited, association input records, rebuilt partitions, and bytes read/written. Target zero observation decoding for ordinary statistics and an unchanged query-view restart; zero rebuilding of unchanged project partitions; and no source replay for price-only changes. These are proposed acceptance conditions, not current behavior. Explicitly report dependency expansion and fallback counts. Required source-integrity verification, conservation, missing-value semantics and evidence retention are not removable work. Moving the same work to startup, a background process or another cache does not establish its removal.

### Research and algorithm fit

The following assessment, researched on 2026-10-11, maps published techniques to this model. The application choices are design inferences, not measured Wombat improvements. Publication dates below are paper or release dates, not search crawl dates. The selection is focused rather than an exhaustive literature review.

| Technique and primary source | Proposed use | Boundary and priority |
|---|---|---|
| [Data Cube, 1997](https://arxiv.org/pdf/cs/0701155): decomposable aggregation | Maintain exact totals and selected task/model/calendar groups from compact facts | First priority for statistics; do not materialize every dimension combination or discard timestamped facts |
| [DBSP, VLDB 2023](https://mihaibudiu.github.io/work/budiu-vldb23.pdf), with a [2025 journal extension](https://link.springer.com/article/10.1007/s00778-025-00922-y) | Model updates as signed relations and compose tested delta operators | Use the correctness model; a generic dataflow engine does not itself bound retained state, memory, or query latency |
| [Enzyme, March 2026](https://arxiv.org/html/2603.27775v1): cost-based view refresh | Select row deltas, affected-partition replacement, or bounded full rebuild using observed work | Borrow the strategy selection. Its Spark/lakehouse runtime and reported speedups do not transfer to an embedded desktop core |
| [Aggarwal–Vitter, 1988](https://www.ittc.ku.edu/~jsv/Papers/AgV88.IO.pdf), and [external hash aggregation, ICDE 2024](https://duckdb.org/pdf/ICDE2024-kuiper-boncz-muehleisen-out-of-core.pdf) | Read bounded batches, partition compact intermediate records, spill, and combine partitions | First priority for rebuild memory. Count temporary I/O and skew; worker-local tables and all queues share one budget |
| [Streaming k-way merge in DuckDB, September 2025](https://duckdb.org/2025/09/24/sorting-again) | Consume sorted runs without materializing the complete merged output | A technique to evaluate through an existing engine; avoid adding a custom general-purpose sorter |
| [Tarjan union–find, 1975](https://doi.org/10.1145/321879.321884) | Use dense integer alias IDs and parent/rank arrays within admitted identity scopes | Secondary hotspot optimization; standard union–find does not split components on deletion. Rebuild affected components and retain global anchor rules |
| [Apache Arrow columnar format](https://arrow.apache.org/docs/format/Columnar.html) | Compare typed batches, validity bitmaps, and bounded dictionary keys with heap-allocated event objects | A layout candidate, not a commitment to Arrow IPC for all storage. Random updates and hash-table workloads can favor compact rows |
| [Temporal aggregate indexes, Yang–Widom, 2001/2003](https://www.vldb.org/vldb_journal/index.php/component/article_manager/article/879) | Evaluate range-summary indexes for time filters that remain expensive after materialization | Later experiment for demonstrated query paths; an ordinary SQL range index still scans matching rows for a sum |

The [PODS 2024 IVM review](https://arxiv.org/html/2404.17679v1) explains tradeoffs between preprocessing, auxiliary state, update work, and answer enumeration. Its results do not provide a universal constant-time algorithm for arbitrary queries and changes. Prefer a small set of persisted aggregates plus dependency-local recomputation. A global repricing or ancestry correction can still affect extensive history. Approximate cardinality sketches cannot replace exact accounting or identity. LSM or Parquet layouts are not a remedy for retaining every decoded event; evaluate them only against a measured remaining storage or I/O problem.

### Bounded computation experiment

First evaluate the verified release build against SQLite with typed facts, persisted aggregates and bounded staging, using the same Rust-produced facts and independent truth. Keep evidence retention identical. Test persisted query reads without safe-event restoration, then full rebuild under a fixed budget, then updates, corrections and dependency closure. Implement the equivalent DuckDB candidate only if measured remaining scans or spill costs justify an engine comparison. A complete general-purpose incremental compiler is outside this experiment; reuse maintained operators and storage implementations where applicable.

Use 100,000, 1,000,000 and 10,000,000 synthetic observations, with identical generation rules and independent expected results. Vary canonical-fact density, unique strings, groups and source sizes separately. Include uniform partitions, one task containing 90% of observations, one oversized identity component, and large valid records. Compare memory budgets of 256, 512 and 1,024 MiB with one and two workers. A provisional experiment gate is rebuild peak RSS at most 512 MiB; the existing steady-state target remains unchanged. These are evaluation targets, not delivered limits. Account for queues, dictionaries, database caches, codec buffers and the complete process tree. Track temporary and retained disk bytes as well as RSS; verify memory pressure does not merely move the cost to swap or unbounded temporary files.

At each scale, test a small append, late detail replacing a cumulative estimate, alias bridge and bridge removal, explicit inheritance correction, price revision, arbitrary timezone/DST boundaries, source loss, restart and interrupted publication. Compare every committed revision with independent full recomputation, including missing/unpriced states and evidence coverage. Repeat the complete foreground latency gate for cold and warm readers, concurrency 1 and 4, and unchanged output sizes. Keep failed scopes visible. A prototype that only parses, tests warm cache hits, skips canonical reconciliation, or drops offline evidence cannot pass.

Select the candidate only after these gates. Record stage times for discovery/verification, parsing, canonical reconciliation, evidence writing, aggregate construction and publication. Full rebuild and incremental maintenance require separate throughput results: delta processing cannot avoid the initial scan. Freeze artifact hashes, corpus hashes and resource settings so repeated runs can test whether an improvement survives scale and skew. A 512 MiB failure requires a revised data path or explicit scope decision, not a higher hidden memory allowance.

### Preliminary technical validation

The [synthetic storage experiment](../../../benchmarks/storage-layout-2026-10-11.json) compares a JSONB layout baseline, compact SQLite with Zstandard blocks, DuckDB with typed facts and the same blocks, and source-backed SQLite. It also compares direct fact scans with four small persisted aggregates. The report records fixture truth, full-event round trips, allocated storage, query distributions, memory, and limitations. These are schema-shaped storage prototypes, not a scan through the Rust adapter.

Prefer SQLite for the next implementation prototype, with small hot aggregates, compact exact facts, verified source locators, and compressed blocks only for retained offline evidence. DuckDB improves broad fact scans in this experiment, but its tested block layout uses more space. Persisted aggregates remove those scans from the common query path without adding a new engine. This does not establish that every DuckDB or Parquet layout is inferior. Defer Parquet and RocksDB implementation experiments until a remaining measured workload justifies the extra storage and publication boundary.

The complete layout comparison uses 300,000 events; the 3,000,000-event baseline exceeded its bounded run time and is excluded from reduction ratios. New layouts completed the larger profile. Source-backed results are a lower bound for the sampled facts: they use generated safe-event ranges instead of raw Codex logs and change offline detail availability. They do not prove complete product size or cold source parsing latency. The harness includes generator and verification memory, so it does not validate the service RSS budget. Actual Rust facts, additional analysis fields, aggregate corrections, restart/crash behavior, cold filesystem reads, concurrency, all platforms, and complete public-entry latency remain required before production adoption.

Reproduce one profile with the entry below and a new output directory. Change the engine to baseline, duckdb, or tiered for comparisons; use 3000000 events and 1200 tasks for scale, and --unique for the separate high-uniqueness profile. DuckDB experiments require an isolated, exact @duckdb/node-api 1.5.6-r.1 installation supplied through --duckdb-module. No production dependency was added.

The [production storage implementation](../../implemented/architecture/2026-10-11-packed-live-index.en.md) removes redundant parser copies, packs retained offline evidence, and adds persisted frame aggregates with bounded query working sets. It does not complete this proposal: full-history parser residency, source-backed detail, strict foreground latency, and the complete scale/concurrency matrix remain open.

### Delivery sequence

| Stage | Work | Exit condition |
|---|---|---|
| 0. Attribute costs | Extend the existing benchmark entry with field/category bytes, event kinds, consumer mapping, read/write counts, and peak storage | Reproducible synthetic baseline; no raw private data; identify unsupported performance claims |
| 1. Select storage and remove repetition | Compare the primary engines, encodings, dictionaries, compact keys, shared payloads, and membership replacement | Exact public results and replay evidence; smaller settled database including every index; select layout from measured alternatives |
| 2. Separate detail | Add verified source ranges, parser context, bounded offline blocks, and decoded caches | Source-backed detail and retained evidence preserve their declared guarantees; small appends and detail reads avoid full archives; meet storage gates below |
| 3. Bound computation | Move reads to stored canonical facts, dependency-local reconciliation, aggregates, and leased versions | No full-event startup or full-source normal append; meet existing memory/query targets and 24-hour growth acceptance |
| 4. Complete recovery | Deliver space reporting, cache reclamation, and authorized index rebuild in both hosts | Interrupted/full-disk/unsupported-format journeys preserve committed data and user state; no silent accumulating generations |

Stages 1 and 2 first compare storage prototypes on bounded fixtures. Do not replace the production writer until identity, replay, and query consumers are covered. Stage 3 is necessary for complete delivery; a smaller database with unbounded restoration is not the final result. No stage needs a production-data rescan merely to prepare this proposal.

## Acceptance criteria

### Storage targets and measurement

Add a deterministic storage profile to the existing benchmark runner: 1,200 files, 3,000,000 safe events, 200,000 measurement candidates, and 250,000 canonical operations. Define and pin the event-kind distribution, task/turn cardinality, path lengths, string uniqueness, and correction ratio before comparing layouts. Run high-uniqueness and poor-compression variants separately. These are synthetic parameters, not copied conversations. Compare the same source fixture and scope against the current release; old local-format measurements do not establish a current-release baseline.

The mandatory acceptance target is at least a tenfold reduction: total settled index storage must be no more than 10% of the baseline for the same corpus and scope. This is a required engineering outcome, not a stretch target or a predicted compression ratio. Smaller intermediate reductions do not complete delivery. For the primary synthetic profile, use 500 MB as an additional provisional absolute budget, pending a frozen baseline; the tenfold requirement remains mandatory if that absolute budget changes. MB here is decimal. Count all fact tables, evidence blocks, dictionaries, indexes, and persistent caches. Do not meet the target by moving data to another directory, omitting history, or counting only compressed payloads. Report bytes per event/measurement and scaling slopes; input-byte ratios alone can be distorted by excluded message bodies. Final budgets must name a frozen fixture, and a miss requires a revised design or explicit business tradeoff.

Measure first scan, restart, no-change refresh, small append, late correction, selected-turn detail, and complete-history queries. Report elapsed time, p50/p95 latency, bytes read/written, peak RSS, database/WAL/temp peaks, and settled allocated bytes after service exit. Include reclamation and rebuild peaks, distinguishing old retained data from the new generation. Unchanged refreshes create no new fact revision or persistent fact growth. Growing history may grow retained facts; fixed-size caches, old versions, and repeated rewrites must not create unbounded amplification. Long lines and incompressible fields must stop or report defined limits without losing valid committed data.

Prove storage changes preserve all exact facts through independent truth and event round trips: timestamps and precision, missing/zero/unpriced distinctions, conflicts, physical-record counts, aliases, parent/child attribution, coverage, and source ordering. Cover source removal after indexing, corrupted blocks, oversized decoded data, canceled decompression, crashes while sealing blocks, late corrections to sealed partitions, expired and active leases, and rebuilds with insufficient free space. Audit source-backed and full-offline profiles separately; a smaller source-backed index cannot pass the full-offline profile by hiding unsupported detail.

### Query latency gate

Storage reduction and query latency must pass together. For ready committed data within the supported fixture and query budgets, require each tested foreground query to return its complete result within 100 ms. Measure elapsed time at the public entry, including dispatch, queueing, IPC or loopback HTTP, database reads, block decompression, business calculation, and response serialization/transfer. For a new CLI invocation, also measure process startup and include it in that entry's request duration. A fast SQL statement does not establish a fast request. Report p50, p95, p99, maximum, and violation count; percentiles do not replace the 100 ms completion gate. State hardware, process state, cache state, concurrency, response size, and corpus before making a claim.

Cover usage totals and daily distributions, task rankings with complete totals, filters across projects/models/timezones, list pagination, selected-turn timing, evidence pages, and existing investigation/review queries within their supported bounds. Test first queries after restart, cold and warm file caches, repeated queries, correction invalidation, and concurrent reads during writes. A cache hit alone cannot pass. Use concurrency 1 and 4 as initial acceptance profiles and report saturation separately. Large valid scopes that cannot complete within 100 ms remain failed acceptance cases until the access path or supported operation contract is explicitly redesigned; silently narrowing the scope or truncating results is not a solution.

Plan hot summary reads around compact canonical tables and bounded materialized aggregates. Precompute only measured common reductions, with complete dependency, timezone, price, and revision keys. Use covering indexes where they reduce measured reads; include their space in the tenfold budget. Detail requests seek a bounded number of evidence blocks. Remove unnecessary process/connection creation and duplicate serialization. Instrument the complete request path before assigning internal time budgets; compressed block size and level must be selected against both storage and cold-detail latency. Do not hide an unbounded scan behind pagination or a response cache.

First collection, full rebuild, source verification, export, and explicitly requested fresh synchronization are separately measured long operations. They need progress, cancellation, and a readable preceding committed view when one exists. An acknowledgement or syncing preview returned within 100 ms is not a completed-query latency pass. If an expensive analysis is redesigned as an asynchronous operation, record job completion time and the changed user contract separately; that change does not automatically satisfy this gate. UI paint time is reported separately from request latency.

### Correctness and recovery

Independent synthetic truth covers modern/legacy cumulative accounting, late-detail retraction, cross-batch model/effort state, duplicate events and reads, parent/child inheritance, cross-file conflicts, late tool results, partial lines, and large lines. Random byte/record splits and restarts must preserve tokens, decimal money, and hierarchical totals against independent truth, not just two implementations that may share a bug.

Inject crashes/cancellation, full storage, lock timeouts, unreadable sources, event overflow, truncation/equal-length replacement/appends with rewrites, archive renames, sleep, data-root changes, and concurrent client starts/exits at transaction boundaries. Verify no duplicate or missing accounting or partial publication, readable committed current-format snapshots, and eventual correction of prefix rewrites with visible detection delay.

Assembled entries must verify fixed-view pagination/drill-down, daylight saving, price switches, reconnects, expiration, stable selection, filter input, and cancellation cleanup. Unchanged sources must not generate meaningless revisions. Windows multiprocess IPC, remote-client rejection, and timeouts need target-system evidence; UI acceptance uses current Web rather than retired terminal journeys.

### Performance targets (pending acceptance)

Use fixed macOS arm64, Node26.4.0+, release, 10,000 files, and 1,000,000 measurements. Twenty active files append 20 records per second in total, at most 1MiB/s, with ordinary lines at most 64KiB. Separately measure valid 1/10/100MiB lines, first indexing, and prolonged backlog rather than mixing them into ordinary append SLOs.

- With an existing index and warm cache, complete-line write to Web display p95 ≤2 seconds; missed-event recovery ≤5 seconds for active files and ≤35 seconds for new files, assuming no sustained backlog.
- First display of older committed results p95 ≤500ms with visible synchronization; ready-data requests must also meet the complete 100 ms query gate above. Report synchronization, pure queries, CLI process startup, cold IPC startup, and cold file caches separately without excluding applicable work from the request gate. Exceeding current query budgets exposes status.
- Ordinary append reads grow with added bytes without rewriting all history; account for full verification and directory sweeps separately. Idle core CPU averages <1% of one core, with service RSS ≤256MiB. Report large-line peaks, host/browser, and total process-tree memory separately.
- First indexing has no two-second promise. Report throughput, elapsed time, memory, disk amplification, and backfill query latency. Run 24 hours to inspect backlog, WAL, fact versions, lease reclamation, and disk growth; unbounded tail buffers or unreclaimed versions fail acceptance.

Persistent views, local reconciliation, database aggregation, and these scale targets remain without full acceptance. Locate reading, reconciliation, transaction, IPC, and rendering costs before tuning, without sacrificing accounting correctness.
