# 使用 Wombat

中文 | [English](plugin.en.md)


Wombat 帮你找回过去的决定、看懂工作用量、定位项目问题，并在修改后复查结果。在 Codex 中直接说明想完成的事，不需要学习命令、寻找会话 ID 或填写一套分析表。

## 从一句话开始

按[安装指南](installation.md)安装后，在 Codex 对话中调用 Wombat。需要明确选择时，使用 `$wombat:wombat`，后面直接写问题。例如：“这周这个项目做了什么，还有哪些没验证？”

不需要初始化项目、先跑全套检查或选择工作流。已经明确的项目、时间和授权会沿用。Wombat 按任务寻找必要证据，不要求用户先知道该查哪种数据。

| 想完成的事 | 可以这样说 | 应该得到什么 |
|---|---|---|
| 找回过去的决定 | “上次为什么改发布流程？把关键讨论找出来。” | 当时的决定、相关原文位置和需要区分的版本 |
| 接续工作 | “接着昨天的工作，先看看做到哪了。” | 已确认的进展、交付位置、未完成事项及下一步 |
| 查看用量 | “看看今天用了多少 Token。” | 对应日期与范围的总量，以及影响结论的数据缺口 |
| 理解用量变化 | “这周为什么比上周用得多？” | 可比范围的变化，任务数量与单任务用量的区分，以及值得查看的记录 |
| 找到工程问题 | “发布总是反复失败，查查之前怎么处理的。” | 失败位置、以前的尝试、当前机制和有依据的最小改动 |
| 改善项目工作方式 | “看看这个项目最值得改善的地方。” | 与实际后果有关的少数问题、具体负责位置和验证办法 |
| 整理 Skill 或 MCP | “哪些 Skill 很占上下文，却很少用？” | 占用估算、使用依据、作用范围，以及逐项取舍建议 |
| 清理工作产物 | “整理这个项目的临时和编译文件，保留交付文件。” | 具体路径、归属、保留条件；授权明确后执行并复查 |
| 确认结果 | “复查刚才的修改，看看原问题还在不在。” | 同条件的验证结果、未执行项及不能下结论的部分 |
| 整理报告或知识 | “把这周的进展和决定整理进项目文档。” | 有来源位置的整理稿，区分完成、未验证和待继续事项 |

这些任务共用一个入口。一次只问总量，就先回答总量；不额外展开排行、工程检查和清理建议。需要组合任务时，Wombat 才把有关结果放在一起。

## 一次诊断项目，选择后完成优化

这个任务帮助你决定：项目现在最值得先改什么，哪些应该保留，怎样确认改动有效。可以直接说“诊断这个项目，给出值得执行的改进”，也可以限定“只看发布和验证流程”。不需要先了解检查种类或准备配置。

### 发起诊断

在 Codex 中调用 Wombat 后，提出一次诊断请求即可。Skill 复用 `wombat check` 获取项目事实，再按发现的线索读取必要记录和当前代码。CLI 的命令与事实输出见 [CLI 指南](cli.md#project-diagnosis)。普通终端命令提供事实报告；完整的判断、修改和验证在当前 Codex 对话中完成，不另起模型会话。

项目默认使用当前明确的目录；无法确定时只询问项目位置，不扩大到主目录。范围包括项目文件、明确作用于该项目的 AI 配置，以及相关工作记录。全局配置只检查对该项目的已知影响，不默认整理其他项目或全部用户缓存。

相关历史默认覆盖最近 30 个本地日，含今天，实际结果写明日期和时区。已经指定的日期或工作范围优先。记录尚未准备好或不存在时，当前文件和配置仍可检查；缺口只限制依赖这些记录的判断，不要求先完成全历史索引。

### 诊断过程

开始时简短说明范围及只读阶段。取证可以更新 Wombat 自身的派生索引，但不改项目、启用状态或原始记录。需要安装依赖、构建、启动服务或执行可能写入及访问外部的验证时，先把操作及影响列入方案，沿用明确的已有授权。

| 要帮助你判断什么 | 起点 | 何时继续深入 |
|---|---|---|
| 工作为什么反复或卡住 | 最近任务、失败和重复操作线索 | 能定位到具体任务时，读取关键轮次并核对当前负责代码 |
| 交付是否得到有效验证 | 项目声明的构建、测试、交付与恢复入口，相关任务的最后进展 | 追踪重要入口的实际调用及对应验证，不把命令成功当作交付完成 |
| AI 工作环境是否合适 | 规则、引用、Skill、MCP、Hook 的当前检查及相关使用依据 | 明确失效、职责冲突或取舍候选值得判断时，再读选中内容 |
| 空间里哪些产物值得整理 | 当前项目的临时和编译产物候选、归属及待使用条件 | 对具体候选核对生成方式、交付用途与保护条件 |

用户只需发起一次请求，内部按依赖组合必要操作。开放式诊断会主动追踪项目重要的执行、验证或恢复路径；不只罗列配置提醒。路径由项目实际入口和近期问题决定，不承诺审计所有代码，也不为了覆盖表格而运行全部分析。

用量、耗时和使用次数帮助选择调查对象，不直接证明问题。发现反复工作后，先核对是否是必要验证、合理重试或不同条件下的调用。长文件、低频 Skill、缺少记录和正常负面测试不能单独成为整改项。

同一机制产生的多个信号放到一个问题中解释，同时保留各自的来源。配置、历史和现场文件可能来自不同读取版本，报告说明影响判断的差异，不把它们称为同一时刻的完整快照。更新进度只说明当前在查什么或遇到什么阻塞，不刷屏列出每条内部调用。

### 报告如何帮助你作决定

报告先给“建议先处理什么”，再按需展开依据。每个整改项都有本次报告内可选择的编号，并说明后果、确认程度、具体文件或操作、最小改动、影响范围及复查条件。优先次序综合实际后果、证据和可执行性；没有总分，也不固定凑几项。

已确认的问题、需要验证的假设和用户需要作出的取舍分开。假设附上能决定下一步的有限调查，不能直接以假设为理由修改代码。证据不足的 Skill 不会因少用就进入“建议删除”。没有足够价值的改动时，报告说明查过什么及边界，允许不作优化。

下面用假设项目展示报告的结构；问题、路径描述和结果均不是本机诊断结论。正式报告会链接实际文件与记录位置。

**建议先补上发布入口校验，再修复引用；编译产物可在验证结束后清理。**

| 选择 | 问题与依据 | 准备执行的优化 | 怎样复查 |
|---|---|---|---|
| 1 | 发布入口未调用已有校验；沿调用链未发现其他保护 | 在该入口复用现有校验，保留正常发布行为 | 相同有效输入通过，原无效输入被阻止；不自动发布 |
| 2 | 项目规则中的一条本地引用失效，已有可确认的替代文档 | 只修正该引用，不重写整份规则 | 原规则检查不再命中，并检查替代文档符合原意 |
| 3 | 选中的编译输出可再生成，但要先用于本次验证 | 验证结束后清理列明的路径，保留交付文件 | 路径处理结果及交付文件完整性；不重建全部产物 |

**覆盖范围：** 当前项目及指定日期内的相关记录。MCP 实际上下文占用未测得；这不妨碍核对已取得的配置证据。全局停用和项目外清理不在这份执行方案内。

编号 1、2、3 仅用于这份报告中的选择，后续刷新不会把新对象加入旧选择。简单任务可以缩短为一段话和一个整改项，用户不必每次阅读整张表。

### 选择执行，或继续调查

你可以说“执行 1 和 3”“只修规则引用”“先验证发布问题的假设”或“这次先不改”。只要求诊断时，报告完成后等待选择。用户已经明确授权相同范围的具体改动时，沿用该授权，不重复索要确认；宽泛的“自动优化”不能代替具体影响说明。

执行方案列明选中对象、改动及保留项、依赖顺序、必要的验证操作和恢复办法。清理选项明确是否永久删除，配置选项明确项目或全局作用范围。说“全部执行”只覆盖当前已展示且可执行的方案，不包括尚未验证的假设、未披露的全局影响或新发现对象。

Codex 在修改前核对选中目标和未提交改动，保留原问题、输入与检查条件。共用同一文件的修改合并处理；验证仍需使用的产物最后清理。执行中遇到的新问题先报告，不自动加入整改。用户可以随时要求停止，后续操作随即停止，已经发生的变更单独说明。

恢复只撤销本次选中的改动，不覆盖用户后来的修改，也不通过重置整个工作区恢复。不可恢复的删除不承诺撤销。相关步骤失败时停止其后续依赖，其他独立项可继续；重试前核对已完成部分，不重新执行整批。

### 得到改后结果

完成后按选中项说明改了什么、原问题是否仍存在、通过哪些验证、哪些未运行，以及保留了什么。配置问题复用各自原始条件的复查，代码机制运行对应案例和项目测试，清理核对原候选；不同类型的结果不用一个“通过”代替。

在上面的示例里，用户选择“执行 1 和 3”后，结果应分别说明发布校验是否覆盖有效和无效输入，以及验证后哪些路径实际被清理。未选择的引用保持原样；没有进行真实发布，就明确列为未验证，不报告“发布验收全部通过”。

规则复查通过、相关测试通过和空间整理完成属于当场可验证的结果。工作是否更顺畅、后续用量是否减少，需要自然产生的可比任务才能判断。诊断不会为此创建额外任务、自动优化历史或持续追踪系统。报告默认留在当前对话中，需要保存时写入你指定的位置。

### 中断和缺口

| 情况 | 怎样继续 |
|---|---|
| 项目位置不明确 | 保留请求，只询问可读的项目位置；不默认扫描父目录或主目录 |
| 历史读取失败，当前文件可读 | 交付当前可确认的发现，标明历史相关判断未完成 |
| 某项检查被截断或超出范围 | 说明该项覆盖到哪里；只为会改变决定的线索继续读取 |
| 没有发现值得处理的问题 | 返回已检查范围和重要缺口，不制造整改项或宣称整个项目没有问题 |
| 确认前文件或启用状态变化 | 重新核对受影响项；实质改变方案时更新说明和选择，不套用旧结论 |
| 原读取视图过期 | 重新检查相同目标，保留已有工作；不伪造旧结果的前后比较 |
| 修改完成但验证失败 | 说明当前变更、失败位置和恢复选项；不能标为已解决 |
| 用户取消或部分执行失败 | 列出完成、未处理及结果未知的操作；继续前先核对实际状态 |

## 对话会是什么样

下面是交互示例，使用假设的项目和结果，用于讨论设计，不是本机分析报告。实际回答只包含已取得的证据，不固定套用相同篇幅。

### 找回决定，然后接着做

**你：** 上次为什么改发布流程？接着做。

**Wombat：** 找到两个可能的任务：A 项目昨天的安装验证失败，以及 B 项目上周的发布检查调整。你要接着哪个？

**你：** A 项目。

**Wombat：** 当时决定把“程序安装成功”和“插件能否被当前项目发现”分开验证。记录里已经修改了提示，但没有找到修改后实际安装的验证结果。相关依据是该任务中作出决定的轮次和最后一次进展；下一步核对当前实现，再验证安装成功但发现失败的分支。

**你：** 先把这个验证补上。

**Wombat：** 我会沿用 A 项目和这次修改的范围，核对后补上验证。完成时分别说明程序安装、项目发现及提示恢复是否通过；尚未运行的分支单独列出。

### 看懂变化，再决定值不值得改

**你：** 这周为什么用量变多了？

**Wombat：** 按两周相同的已完成星期比较，用量增加主要来自任务变多。今天尚未结束，未纳入这次比较。这个结果还不能说明存在浪费，需要看具体任务里是否有可减少的反复工作。实际回答会列出两边的日期和统计依据。

**你：** 只看这个项目，有没有白做的？

**Wombat：** 我会沿用刚才的日期，只查看当前项目用量变化最大的有关记录。必要的失败测试和修改后的复查会保留；如果发现代码没有变化、结果仍有效，却重复运行同一项检查，就定位那几次调用及触发位置，再建议减少重复检查。缺少运行条件时不能认定它们白做了。

### 从工程问题走到可验证的修改

**你：** 看看发布流程有什么值得改的。

**Wombat：** 发布入口没有调用已有的输入校验；校验函数本身已有测试，但当前调用链上也没有其他保护，所以无效输入仍可能进入发布。建议在发布入口复用现有校验，保留正常发布行为，并补上无效输入被阻止的验证。实际回答会标出入口、校验函数和测试的具体文件位置。

**你：** 按这个改，然后确认原问题解决了。

**Wombat：** 我会修改这个入口，并验证有效输入仍可发布、原来的无效输入会被阻止。复查保留相同输入和判断条件；如果只跑了本地检查，就明确说明尚未完成真实发布验证。

### 整理环境时作出有依据的取舍

**你：** 把很占上下文又没用的 Skill 去掉。

**Wombat：** 我会先找占用估算较高、使用记录较少的候选，再核对职责。这里估算的是 Skill 发现目录中说明文字的 Token，不等于实际上下文占用；没有使用记录也不能证明没用。候选会分别列出来源、项目或全局范围，以及建议保留、按需启用或停用的理由。

**你：** 这个发布用的保留，另一个只在当前项目停用。

**Wombat：** 我会先确认它支持当前项目范围的调整。支持时保留恢复所需的原值，调整后检查状态及仍需使用的能力；如果只能全局停用，就说明影响并停在这里，不替你扩大范围。

### 清理后确认保留的东西还能用

**你：** 清理这个项目的临时和编译文件，交付文件别动。

**Wombat：** 我会先核对具体路径、生成方式和后续用途。确认可再生成且不再使用的编译产物按本次授权清理；交付文件和归属不明的目录保留。项目以外的 Codex 缓存不在这次范围内。

**你：** 好，清理完看看有没有影响。

**Wombat：** 我会说明实际处理与保留的路径，再检查交付文件及受影响的项目操作。如果清理被占用或保护条件阻止，就报告未处理项；不会把部分清理说成全部完成，也不会为验证而重建所有刚删除的产物。

## Wombat 会怎样配合你

### 理解目标和范围

“这个项目”沿用当前明确的项目；“今天”“这周”按你的本地时区解释，并在结果中写明实际日期。只问整体用量时，查看已授权记录来源中的全部项目。用户指定项目或日期后，后续查找和读取保留该限制。

上下文已有答案时不重复询问。不同选择会改变结果、读取范围或修改对象时，再问一个具体问题。例如多个项目都有“发布失败”记录时，先展示项目、时间和主题供选择，不要求用户识别内部 ID，也不默认选择第一条。

“上次那个”“刚才的修改”沿用本对话中已经确定的对象。新对话缺少该上下文时，先找到候选或说明缺什么，不假装记得另一段对话中的选择。

### 先回答，再给依据

简单问题给出简短结论、范围和必要说明。复盘或诊断则说明发现了什么、依据在哪里、建议改什么，以及怎样复查。关键讨论提供可定位的原文，项目修改提供明确文件或操作位置。

用户通常不需要看到 CLI 命令、JSON、读取视图或内部状态码。只有手动重现、脚本集成或故障处理需要时才展开这些细节。结果使用用户的语言，记录原文与模型名称保持原样。

数据还在准备时，说明哪部分已知、哪部分未完成。没有找到记录、尚未查完和无法读取是不同情况。不会把未知用量填成零，也不会因局部证据缺失就让用户反复重装。

### 给能执行的建议

建议应包含具体后果、证据位置、负责文件或操作、最小改动及复查办法。提出改动前，先核对已有机制和可能推翻结论的证据。

例如，发布路径绕过已有校验时，有用的建议是：在现有发布入口接入该校验，保留原行为，并验证有效输入可以通过、对应无效输入会被阻止。仅说“加强测试”“精简配置”或“换小模型”不足以指导修改。

“看看值得改善的地方”会主动检查重要的执行、验证或恢复路径，而不是等用户逐项指出问题。已有确定的当前代码问题，不强制查历史；历史能改变判断时，才定位相关记录。不为了凑数量制造问题或给项目打总分。

### 按已有授权推进

查找和分析先读取证据。用户已经明确要求、且范围清楚的修改或清理，可以继续完成，不在每一步重新索要确认。仅要求分析或设计时，不擅自修改文件。

授权不足以确定具体对象或影响时，先准备可审查的结果，再提出选择。例如“删掉没用的东西”不能直接变成删除整个目录；应先说明路径、归属、保留项和实际影响。过去记录里的“可以删除”不等于本次授权。

修改涉及其他项目、全局配置、永久删除、对外发送内容或定期执行时，明确说明其实际范围，并沿用或取得与该范围相符的授权。取消后停止后续操作，已经发生的变更和未完成部分分别说明。

### 回到原问题复查

修改前保留原问题和判断条件，修改后重新运行相关检查或原来的项目测试。用户可以直接说“按刚才的条件复查”，不必重新填写技术参数。

结果区分已通过、仍存在、未执行、证据不足和条件不可比。检查没有发现问题，不等于交付已经被用户接受；运行命令成功，不等于它测试了正确的行为。原证据失效时重新检查，不能把新结果伪装成旧的前后比较。

## 找回决定并接续工作

找历史时，先定位有关工作和关键对话，只读取需要的片段。长会话按日期、轮次和位置继续，不把整段记录全部塞进当前对话。明确给出的日期与项目边界不会因打开记录而扩大。

接续工作时，应交付三类信息：已经确认做到哪里、相关文件或交付在哪里、接下来哪件事最有用。记录中写着“完成”时，若实际文件或验证结果尚未核对，就明确标为待验证。

可以继续说：“只看最后的决定”“展开失败前后的讨论”“先完成没做完的验证”。这些请求沿用已选对象，无需重新搜索同一批记录。

## 看懂用量及变化

只问“今天用了多少”，就给今天对应范围的用量和完整性说明。问“谁用得最多”才展开排行；问“为什么变化”才比较日期、任务分布和相关记录。

比较时先说明两边的实际日期、项目和数据是否可比。任务变多与单任务用量变高是不同线索；较高用量不自动表示浪费，较低用量也不自动表示工作质量提高。

当变化集中在某些记录时，再定位相关过程，判断是否值得调整。时间、操作结果或来源身份不完整时，保留不确定性。费用或账户额度只在需要时单独说明，不把估算当成账单，也不从记录推算订阅余额。

可以继续说：“只看这个项目”“定位变化最大的几条记录”“看看是不是必要的验证”“改完以后用同样口径再比”。最后一种比较还需要工作量与质量条件可比，不能只比较总 Token。

## 复盘并改善工程问题

已知失败时，先回到原始失败、已有尝试和当前负责位置。用户要求开放式复盘时，主动寻找重要路径上的真实缺口，说明触发条件和后果。

重复读取、失败后重试、输入量增长和等待时间都是检查线索。正常负面测试、必要复核或合理重试不应被误报成问题。需要判断代码行为时，Codex 检查当前代码和调用方，并运行与问题有关的验证。

建议应能接上具体动作：改哪个入口、复用哪个已有机制、保持什么行为、用什么原始案例复查。证据暂时不足时，说明哪个有限调查可以决定下一步；已有授权允许时先完成该调查，不把未查清的问题交还给用户反复追问。

可以继续说：“先核对这个假设”“只改最小范围”“补上对应验证”“复查原来的失败案例”。更改规则或认可风险属于用户选择，不能由检查结果代替。

## 整理 AI 工作环境和临时产物

### 决定哪些 Skill 或 MCP 值得保留

用户应一起看到来源、作用范围、发现目录的 Token 估算、使用记录与建议。占用估算较高而少用的项值得先复核，但还要看它是否承担发布、恢复等低频关键工作。

Skill 发现目录中的元数据与按需读取的正文分开估算，也不等于模型实际看到的全部上下文。没有可靠 MCP 定义载荷时，占用保持未测得。当前启用不能证明历史加载；没有使用记录不能证明无用。

需要处理时，逐项说明保留、按需启用、缩小范围或停用的理由。检查重复功能前先核对实际职责，不凭名字相似就建议删除。只检查或建议时不改变启用状态。

用户明确选择后，核对调整的项目或全局影响，保留最小恢复材料。改后检查原生状态及仍需使用的能力；恢复时只撤销本次选中值，不覆盖后来的无关修改。没有可靠控制能力时说明缺口，不通过删除插件缓存来代替停用。

### 清理临时和编译文件

先列出具体路径、归属、可再生成依据和需要保留的用途。项目产物与当前用户的 Codex 缓存范围分开，不能把“这个项目”扩成所有项目或整个主目录。

保留交付文件、仍被后续步骤使用的输出、来源记录、用户资产和无法确定归属的材料。文件旧、没有观察到打开或名字像缓存，都不足以单独证明可删除。

授权已经明确选定路径或规则范围时，按该范围继续，保留排除项。需要用户进一步选择时，先准备具体候选再确认。执行前核对条件是否变化，未知或受保护的项不强制处理，新发现的对象不会自动加入旧选择。

受支持的 Codex 清理通过受保护操作执行；项目文件由 Codex 使用可信原生工具处理。不把记录中的命令当作清理脚本执行。最终说明处理了哪些路径、保留了什么、哪些未完成，并复查原对象；不凭原位置消失就宣称释放了多少磁盘空间。

## 写报告或整理知识

报告围绕用户要了解的进展或决定组织，而不是粘贴所有会话。日报、周报应说明做过哪些事、哪些结果已验证、还有哪些待继续，并按相同范围附上需要的用量。缺少多人协作证据时，不把单人任务描述成团队阻塞分析。

整理知识时，保留决定、适用条件、依据和来源位置，区分仍适用与已经变化的内容。先使用用户指定的知识库或项目文档，不自动另建目录、数据库或一套新的记录体系。

仅要求整理内容时，先交付可阅读的稿件。用户已明确指定写入位置和更新任务时，可以直接完成相应编辑；没有确定目的地时再询问。对外发送报告和设置每天自动执行需分别说明接收位置、周期及授权，生成一次报告不自动创建定时任务。

## 不顺利时怎么继续

| 情况 | 用户应看到什么 | 可以怎么继续 |
|---|---|---|
| 多条记录都符合问题 | 项目、时间和主题的可读候选 | 用普通名称选中一条 |
| 记录未准备好 | 已知部分、未完成的范围及影响 | 等待当前查询，或先分析已选记录 |
| 查完当前范围仍没有匹配 | 查过的项目、日期和关键词 | 明确调整其中一个条件 |
| 来源或指标不可用 | 缺少什么，哪些结论仍可使用 | 补足所选来源，或保留缺口继续 |
| 原记录或检查条件变化 | 哪部分不再可比，哪些操作尚未完成 | 按原目标重新检查 |
| 删除或修改被保护条件阻止 | 具体对象与原因，已完成及未处理的部分 | 重新核对对象，不扩大或强制执行 |
| 安装正常但发现失败 | 分项状态和受影响的功能 | 处理具体发现或资源问题，不重复重装 |

已经得到足够证据回答问题时结束，不为了显得全面继续扫描或固定追加提醒。仍有关键缺口时，说明它怎样影响当前决定，以及哪个具体观察能补齐；不把失败、缺失或超时包装成成功。

## 更新与移除

按[安装指南](installation.md)更新运行时和插件。`wombat system update` 只更新运行时；运行程序、插件资源与当前项目发现状态需要分别确认。用户通常只需说明“检查 Wombat 是否可用”，再按具体结果继续。

Codex 管理插件。确定要移除时，使用其插件管理入口；命令行方式如下。

```sh
codex plugin remove wombat@wombat-local
```

移除插件保留产品数据。Wombat 不自动注册 Hook，也不单独安装另一份 Skill。普通历史与用量查询无需 Hooks；需要特殊观察时再明确配置。

## 结果与边界

Wombat 的本地查询不调用模型；当前 Codex 对话中的分析、编辑和验证使用宿主模型。原始工作记录保持只读。事实读取、用户决定、授权修改与验证结果分别处理。

Skill 为这些任务组织证据与行动，不保证每个问题都有历史记录、每个指标都可计量，也不把静态检查当作完整交付验收。更细的范围和自动化接口见 [CLI 完整指南](cli.md)；普通使用不需要先学会它们。
